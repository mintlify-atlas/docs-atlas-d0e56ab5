title: "Quickstart: Install, Start Docker, and Run a Backtest"
sidebarTitle: "Quickstart"

By the end of this guide you will have run a complete single-month backtest end-to-end: dependencies installed, persistence up, the engine simulating a weekly index fund over one calendar month, and a JSONL report on disk ready to inspect. From there you can replay all 73 months in one command and fold every result into a summary table.

<Note>
**Prerequisites before you begin:**
- **Node.js 18+** — the CLI and scripts require the modern `fetch` API and ESM support.
- **TypeScript 5+** — listed as a peer dependency; install globally or let `npm install` resolve it locally.
- **Docker with the Compose plugin** — both persistence services are defined as Compose files. The classic `docker-compose` (v1) binary also works if you substitute it for `docker compose`.
</Note>

<Steps>

<Step title="Install dependencies">

From the repo root, run:

```bash
npm install
```

This installs the full backtest-kit suite — `@backtest-kit/cli`, `backtest-kit`, `@backtest-kit/mongo`, `@backtest-kit/ui`, and all supporting packages — as well as utility libraries (`dayjs`, `ioredis`, `mongoose`, `functools-kit`). No separate build step is needed; the CLI compiles and executes TypeScript strategies directly.

</Step>

<Step title="Start persistence">

The engine requires both MongoDB and Redis before it will load any strategy. Start them with the Compose files in the `docker/` directory:

<CodeGroup>

```bash Linux / macOS
docker compose -f docker/mongo/docker-compose.yaml up -d
docker compose -f docker/redis/docker-compose.yaml up -d
```

```powershell Windows (PowerShell)
docker compose -f docker/mongo/docker-compose.yaml up -d
docker compose -f docker/redis/docker-compose.yaml up -d
```

</CodeGroup>

MongoDB starts on port `27017` with a persistent volume at `docker/mongo/mongo_data/`. Redis starts on port `6379` with password `mysecurepassword` (set `CC_REDIS_PASSWORD=mysecurepassword` in a `.env` file at the repo root to match).

`config/loader.config.ts` exports an async function that calls `waitForInit()` from `@backtest-kit/mongo`. The CLI blocks strategy loading until both connections are confirmed — if either service is unreachable you will see a connection timeout rather than a cryptic runtime error.

<Note>
Candle data is **never written to MongoDB**. Each month's `backtest.module.ts` calls `PersistCandleAdapter.useDummy()`, so the synthesized minute candles stay in memory. Only signals, sessions, and state documents land in Mongo.
</Note>

</Step>

<Step title="Run a single month">

```bash
npm start -- --backtest --ui --entry ./content/sep_2020/main.strategy.ts
```

Flag breakdown:

| Flag | Effect |
|---|---|
| `--backtest` | Runs the engine in backtest mode: positions are simulated against historical candles fetched from Yahoo Finance, not a live exchange. |
| `--ui` | Serves a local browser UI where you can watch signals and equity update in real time as the engine steps through the month. Omit for headless runs. |
| `--entry` | Path to the strategy file to execute. Each month folder is fully self-contained, so this single flag is all that changes between months. |

The engine steps through the month one day at a time (`CC_BACKTEST_STEP_MINUTES: 1440` is set inside the strategy). Each weekly position opens with `Position.bracket`, holds for `HOLD_MINUTES` (one week minus one minute), and closes by `time_expired`. When the month's frame ends the process calls `kill()` and exits with a non-zero code — this is expected and normal.

<Tip>
Try September 2020 (`sep_2020`) as your first run: it is the reference month from which all others are generated, and its basket is well-documented in the source comments.
</Tip>

</Step>

<Step title="Run all 73 months in sequence">

<CodeGroup>

```bash Linux / macOS
bash scripts/linux/generate_strategy.sh
```

```batch Windows (Command Prompt)
scripts\win\generate_strategy.bat
```

</CodeGroup>

The runner script iterates every month folder in chronological order and invokes `npm start -- --backtest --entry` for each one. Each month's engine process exits with a non-zero code when the backtest frame ends (via the engine's internal `kill()` call). Both runners treat this as a normal completion, not an error, and continue to the next month.

Each completed month writes its report to `content/<month>/dump/report/backtest.jsonl`. If `opened` count does not equal `closed` count in a month's report the run was interrupted — re-run that month individually to complete it.

</Step>

<Step title="Summarize all results">

Once all (or some) months have run:

```bash
node scripts/common/summarize_reports.mjs
```

This scans every `content/*/dump/report/backtest.jsonl` file and prints a consolidated table. Columns:

| Column | Meaning |
|---|---|
| `month` | Calendar month (e.g. `sep_2020`) |
| `opened` | Number of positions opened during the month |
| `closed` | Number of positions closed (should equal `opened`) |
| `net$` | Net P&L in USD across all symbols for the month |
| `net%` | Net return as a percentage of total deployed capital |
| `fees$` | Engine-estimated trading costs for the month |
| `gross%` | Gross return (net P&L plus estimated round-trip fees added back) |
| `PAXG$` | P&L contribution from the PAXG (gold) counter-position |
| `gate` | Min–max gate value observed during the month, formatted as `min..max` (0 = fully in gold, 1 = fully in alts) |
| `non-time closes` | Count of positions that did **not** close via `time_expired` — each one is worth investigating for data issues |

The script also prints a cumulative P&L and drawdown summary across all months.

</Step>

</Steps>

## What to Look for in the Report

Each month's report is at `content/<month>/dump/report/backtest.jsonl`. Every line is a JSON object with a top-level `symbol` and a `data` object whose `action` field identifies the row type:

```jsonl
{"symbol":"BTCUSDT","data":{"action":"opened","cost":46.3,"time":1598918400000,...,"payload":{"gate":0.5,"weight":0.0463,"basketSize":20}}}
{"symbol":"BTCUSDT","data":{"action":"active","time":1599004800000,...}}
{"symbol":"BTCUSDT","data":{"action":"closed","closeReason":"time_expired","pnlCost":2.14,...}}
```

Key things to check:

- **`closeReason: "time_expired"`** is the normal, expected exit. Every position is designed to run for exactly one week and close on the time limit. Any other close reason (stop-loss, take-profit, or manual) indicates an unusual data event and should be investigated.
- **`payload` on `opened` rows** carries three fields that describe the market state at entry:
  - `gate` — the Bitcoin trend gate value (0–1) at the moment the position was opened. This determines how much of the deposit is in alts vs. PAXG that week.
  - `weight` — the fraction of `DEPOSIT_USD` allocated to this symbol: `gate / basketSize` for each alt in the basket, `1 − gate` for PAXG.
  - `basketSize` — the number of alt symbols in the basket for that month (20). PAXG is tracked separately as the counter-position and is not counted in `basketSize`.
- **`pnlCost` on `closed` rows** is the realized P&L for that position in USD. Sum these across a month to get the net result, or use `summarize_reports.mjs` to do it automatically.

<Note>
If `opened` ≠ `closed` for a month, the backtest run was interrupted mid-month. Re-run that month with `npm start -- --backtest --entry ./content/<month>/main.strategy.ts` to complete it. The engine will resume from where it left off using the state stored in MongoDB.
</Note>
